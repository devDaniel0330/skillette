# Project Proposal

## 1. Purpose

This skill provides guidance for creating clear, structured, professional and well-organized project proposals.

The goal is to produce proposals that communicate the project's purpose, justification, objectives, scope, methodology, timeline and expected outcomes.

Adapt the proposal structure and writing style according to the project type, audience, and submission requirements.

## 2. General principles

Follow these principles when preparing project proposals:

- Maintain a formal and profesisonal writing style.
- Use clear, concise and grammatically correct language.
- Ensure every section contributes meaningfully to the proposal.
- Maintain logical consistency between sections.
- Avoid unnecessary repetition and overly complicated sentences.
- Do not introduce unsupported facts, statistics or assumptions.
- Use consistent terminology throughout the proposal.
- Explain technical concepts when the intended audience may not be familiar with them.
- Ensure the proposal is realistic and achievable.

## 3. Before writing

Before drafting a proposal, include the following information:

1. Project title
2. Project background and context
3. Problem or opportunity being addressed
4. Project purpose and justification
5. Intended objectives
6. Project scope and limitations
7. Target users or stakeholders
8. Proposed methodology or approach
9. Project duration and timeline
10. Expected outcomes and deliverables

If any other important information is missing, ask the user for clarification rather than inventing details.

When the user provides an existing document, template, or institutional guidelines, prioritize those requirements over the default structure in this skill.

## 4. Standard Project Proposal Structure

Use the following structure as a starting point. Modify it according to the project requirements.

### 4.1 Project Title

- Use a concise and descriptive title.
- Clearly communicate the project's main purpose.
- Avoid unneccessary long or vague titles.

### 4.2 Introduction / Background

Explain the context and circumstances surrounding the project.

Include:
- General introduction to the project area.
- Existing situation or current practices.
- Relevant background information.
- Context that helps readers to understand the project.

The introduction should gradually establish why the project is necessary.

## 4.3 Problem Statement

Clearly identify the problems or challenges the project intends to address.

Guidelines:
- Describe the existing situation.
- Identify specific weaknesses, inefficiencies, or limitations.
- Explain the consequences of these problems.
- Establish why an improvement or solution is needed.

Avoid presenting solutions before the underlying problems have been clearly explained.

### 4.4 Project Objectives

Write objectives that describe what the project intends to achieve.

Guidelines:
- Use specific and measurable objectives where possible.
- Begin objectives with action verbs.
- Ensure each objective supports the overall project purpose.
- Keep objectives realistic and achievable.
- Avoid vague objectives such as "make the system better".

Examples of action verbs:
- Develop
- Design
- Implement
- Evaluate
- Analyze
- Improve
- Automate
- Integrate

### 4.5 Project Scope

Define the boundaries of this project.

Include:
- Main features or components.
- Target users.
- Functional coverage.
- Areas included in the project.
- Areas explicitly excluded from the project.

For software projects, distinguish between functional scope and user scope where appropriate.

Do not describe features as project deliverables unless they are actually intended to be implemented.

### 4.6 Project Significance / Justification

Explain why the project is important and who benefits from it.

Consider:
- Operational improvements.
- Time and resource efficiency.
- Improved accuracy.
- Better user experience.
- Organizational benefits.
- Academic or technical contributions.

Relate each claimed benefit to the project's actual objectives.

### 4.7 Methodology

Explain how the project will be carried out.

Depending on the project type, this may include:
- Research methodology.
- System development methodology.
- Data collection methods.
- Tools and technologies.
- Implementation procedures.
- Testing and evaluation methods.

For software development projects, explain the development phases and the activities performed during each phase.

Do not select a methodology merely because it is popular. Ensure it is suitable for the project's requirements.

### 4.8 Project Timeline

Present the project schedule in a clear and organized format.

A timeline may include:
- Project phases.
- Activities.
- Estimated durations.
- Start and end periods.
- Expected milestones.

Use a table or Gantt chart when appropriate.

Ensure the timeline is realistic and consistent with the proposed methodology.

### 4.9 Expected Outcomes

Describe the results expected upon project completion.

For software projects, these may include:
- A functional application.
- Improved operational processes.
- Reduced manual work.
- Better information management.
- Improved accessibility and usability.

Distinguish expected outcomes from actual results. A proposal describes anticipated results, not completed achievements.

### 4.10 Conclusion

Summarize the proposal by reiterating:
- The problem being addressed.
- The proposed project.
- Its main objectives.
- Its anticipated benefits.

Avoid introducing major new information in the conclusion.

### 4.11 References

When external information is used:
- Include appropriate citations.
- Use the citations style specified by the user or institution.
- Ensure every cited source appears in the reference list.
- Never fabricate authors, publication dates, titles, or URLs.
- Prefer credible and authoritative sources.

## 5. Writing guidelines

### 5.1 Language and tone

Use formal academic or professional English by default.

Prefer:
- Clear and direct sentences.
- Consistent terminology.
- Objective statements.
- Appropriate technical vocabulary.

Avoid:
- Casual expressions.
- Unsupported claims.
- Excessive promotional language.
- Unnecessary repetition.
- Ambiguous statements.

### 5.2 Paragraph organization

Each paragraph should communicate a coherent idea.

A recommended structure is:
1. Introduce the main point.
2. Explain the point.
3. Provide relevant supporting details.
4. Connect discussion to the project.

Avoid excessively long paragraphs that contain multiple unrelated ideas.

### 5.3 Section consistency

Check that the proposal sections are logically connected.

For example:
- The objectives should address the problems identified in the problem statement.
- The project scope should support the objectives.
- The methodology should explain how the objectives will be achieved.
- The timeline should reflect the methodology.
- The expected outcomes should correspond to the objectives.

## 6. Software development project proposals

When preparing proposals for software development projects, pay additonal attention to the following:

### 6.1 Existing system

Explain how the current process or system operates.

Identify:
- Existing workflows.
- Manual procedures.
- Currnet technologies.
- Operational difficulties.
- Limitations of the existing approach.

Do not assume an organization has a particular system or procedure unless the user confirms it.

### 6.2 Proposed system

Describe the proposed software solution.

Explain:
- What the system will do.
- How users will interact with it.
- How it addresses the identified problems.
- What improvements it introduces.

### 6.3 Functional Requirements

Identify the system's intended functions.

Examples:
- User authentication.
- Record management.
- Data registration.
- Search and retrieval.
- Report generation.
- Administrative management.

Only include features that fall within the proposed project scope.

### 6.4 Non-functional requirements

Consider relevant quality requirements such as:
- Security.
- Performance.
- Usability.
- Reliability.
- Maintainability.
- Compatibility.

### 6.5 Tools and technologies

Explain the proposed technologies and their intended purposes.

Examples:
- PHP for backend development.
- MySQL for database management.
- HTML and CSS for interface development.
- JavaScript for client-side interactions.

Do not recommend technologies without considering the project's requirements and constraints.

## 7. Reviewing existing proposals

When reviewing an existing proposals:
1. Check whether all required sections are present.
2. Evaluate the clarity of the problem statement.
3. Check whether objectives are specific and achievable.
4. Identify inconsistencies between sections.
5. Evaluate whether the scope is realistic.
6. Check whether the methodology addresses the objectives.
7. Review the timeline for feasiblity.
8. Check grammar, clarity and formatting.
9. Identify unsupported claims or missing references.

When suggesting improvements, explain why a change is necessary.

Preserve the original intent unless the user requests a substantial revision.

## 8. Handling templates and requirements

When the user provides a proposal template or institutional guidelines:
- Follow the provided section order.
- Preserve required headings.
- Follow specified formatting and citaton rules.
- Respect word limits and page limits.
- Do not remove mandatory sections.
- Identify conflicts between the template and general recommendations.

The user's provided requirements take priority over this skill's default structure.

## 9. Output guidelines

When generating a project proposal:

- Use clear section headings and subheadings.
- Maintain consistent numbering.
- Use table for structured information where appropriate.
- Use bullet points for lists of features or requirements.
- Keep terminology consistent.
- Ensure the document is ready for further editing or submission.

When appropriate, provide the complete proposal rather than disconnected paragraphs.

If information is unavailable, use clearly marked placeholders instead of inventing details.

## 10. Final quality checklist

Before presenting the completed proposal, verify the following:

- [ ] The project title accurately represents the project.
- [ ] The introduction provides sufficient background.
- [ ] The problem statement identifies clear problems.
- [ ] The objective addresses the identified problems.
- [ ] The project scope defines clear boundaries.
- [ ] The justification explains the project's significance.
- [ ] The methodology is appropriate and understandable.
- [ ] The timeline is realistic.
- [ ] The expected outcomes align with the objectives.
- [ ] References are accurate and properly formatted.
- [ ] Grammar and terminology are consistent.
- [ ] No unsupported information has been introduced.
- [ ] All user-provided requirements have been followed.

Only present the proposal as complete after checking the applicable requirements.
